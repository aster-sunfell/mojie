# Agent run transaction boundaries

This describes the implemented three-layer backend for [Agent Tool Loop PRD v0.1](../prd/Agent_Tool_Loop_PRD_v0.1.md), updated on 2026-10-02. The [refactoring design](Backend_Three_Layer_Refactoring_v0.1.md) defines the layer boundaries; [verification](../verification/backend-three-layer-refactoring-2026-10-02.md) records the regression results.

All short transactions are owned by services through `TransactionRunner`, implemented with Spring `TransactionTemplate`. JDBC repositories acquire the transaction-bound connection via `DataSourceUtils` and do not commit, roll back or change auto-commit. Every participant in a chapter save joins the same REQUIRED transaction. Consistent snapshots use an independent read-only REPEATABLE READ transaction, including when the caller already has a READ COMMITTED transaction.

1. `ContentReadService.versions` reads chapter ID, order and version in one short consistent snapshot. `ToolContentService.captureChapterView` selects the target's admission version and previously read versions, then locks the run and writes the complete view through `ChapterViewRepository` in a separate short transaction. Search scans immutable revisions only after the view commits. Query cancellation is a portable `QueryCancellation` callback; statement and lock timeouts stay in JDBC support.
2. `RunTraceService.modelStarted` locks the run, validates committed input-message references, reserves one model call, and writes the call plus `model.started` event in one transaction. The model request occurs after commit.
3. `modelFinished` writes complete ordered assistant blocks, the call result and the event atomically. `toolStarted` reserves one tool call and writes the step plus event. `toolFinished` writes the actual result, optional reply message, evidence, text budget and event atomically. A result not returned to the model has no reply message and cannot appear in subsequent `input_message_seqs`. Trace persistence failure stops the loop.
4. `RunCompletionService.finish` locks project then run, checks an already committed result first, arbitrates cancellation, deadline, failure and success, validates the final model call and its complete target-chapter input, and commits status, optional proposal, closed records, terminal event and conditional slot release together. Only success publishes a candidate. Repeating finish returns the committed result, including after a lost commit acknowledgement.
5. `RunService.submit` performs the initial idempotency lookup and capacity reservation outside the admission transaction. `RunAdmissionService.create` locks the project, rechecks idempotency and the slot, checks the target chapter version, and commits the run, snapshots, initial message, queued event and active slot together. A uniqueness failure rolls back before a fresh transaction reads the winner. An existing receipt releases the caller's unused reservation.
6. `BoundedRunExecutor` holds ten permits and a two-worker/eight-queue executor. A complete `RunHandle` enters `RunRegistry` before scheduling. Reservation ownership transfers once to the handle. Queued cancellation removes the task and releases once; running cancellation sends the signal and interrupts the task, but the permit is released only when the worker exits. Closing the executor also releases queued reservations.
7. `RunLifecycleService` claims queued work once, records running cancellation requests, settles queued cancellation, finds overdue tasks and fails old-process tasks. `StartupLifecycle` runs Flyway, cleans old tasks, starts `TimeoutSweeper`, then opens readiness. The two-second sweep commits database timeout decisions before signalling local handles. A late response cannot replace a committed terminal state.
8. `ProposalService.accept` locks project, proposal, then chapter. A matching base updates content through `ChapterService`, writes one AGENT revision and marks APPLIED in the same REQUIRED transaction. A version mismatch commits CONFLICTED and returns a result for HTTP 409; it does not throw a rollback-causing exception. Repeat acceptance returns the saved version. Reject preserves already applied item decisions, ignores unresolved items and settles to APPLIED or REJECTED according to the stored review history. Proposal decisions do not append events to the already terminal run.
9. `ChapterSaveCoordinator` locks project, all requested proposals in stable ID order, then chapter. It validates the expected version and decisions, writes changed content and one MANUAL/MIXED revision through `ChapterService`, saves decisions and links every affected proposal to the version. Identical content does not create a version; new valid decisions may still be saved and linked. Invalid or conflicting reviews roll back the complete operation.
10. `AgentRunner` retains a failed terminal identity through the executor's pending-terminal port and stops further model work. `TimeoutSweeper` retries `RunCompletionService.finish` after storage recovers and clears a pending identity only after success. A rejected schedule uses the same compensation mechanism with SCHEDULING_FAILED. Readiness is degraded while a pending identity or sweep failure exists; restart cleanup handles process loss.

The write lock order is `project → run / proposals in stable ID order → chapter`. A trace transaction that locks only run never subsequently requests project. Event `seq` and message `message_seq` are allocated under the run lock and committed with their records. Activity-slot release always matches `active_run_id` to the current run. Model requests, SSE sends, thread waits and full-text scans occur outside database transactions.

`RunQueryService.detail` and developer traces read independent consistent snapshots; traces redact opaque provider blocks. `RunEventQueryService` checks ownership and returns committed events to the Spring-managed `agent.api.sse.RunEventStream`. Its timer, delivery workers, 20-connection limit and once-only release are independent of Agent workers.

## 连续对话与 Skill 扩展（2026-10-02）

新 Conversation 入口由 [连续对话与 Skill 设计](../design/conversation-skills.md) 承接。旧 CHAT 类型已移除；CHAPTER_REVIEW 不提供 propose_chapter_edit，CHAPTER_EDIT 保留当前基准全文与作者采纳边界；旧 Run API 保持原预算和独立任务语义。新任务 16 次模型/32 次工具、120000 新增工具码点和 300 秒运行预算，存入配置快照；请求保存历史来源 ID 与完整逻辑输入。终态展示消息和对话活动槽在数据库事务内收尾。

Skill 目录固定于 Run，版本包在文件卷不可变保存，PG 保存状态及引用；Skill 指导不授予权限。新增 context.compacted、skill.loaded、script.started、script.finished、artifact.created 持久化事件，继续使用按 Run 序号恢复的 SSE。文件下载 attachment/nosniff。独立脚本沙箱及协调备份见 [运维说明](../design/conversation-skills-operations.md)。

2026-10-12 更新：章节工具改名为 propose_chapter_edit，新增设定修改建议、设定版本与修订历史，以及后端禁用修改工具的“仅分析”选项；CHAT 不再接受，历史记录迁移为 ASSISTANT。当前协议以 [章节与设定修改建议](setting-edit-proposals.md) 为准。
