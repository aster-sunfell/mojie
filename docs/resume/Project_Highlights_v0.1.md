## 1. 显式 Agent 工具循环（核心亮点）

**业务需求：** Agent 要按需查阅章节和设定再给出建议，不能声称"已读过"未实际读取的内容，也不能无限消耗模型调用。

**技术实现：**
- 不引入 LangGraph 等通用编排框架，自行实现"请求模型 → 校验响应 → 串行执行工具 → 回填结果 → 再请求"的循环（PRD 5.5）。
- 七个原子工具，按"动词_资源"命名：章节与设定各有 `list_*`（枚举元数据）、`read_*`（完整内容，作为证据）、`search_*`（字面定位，只返回摘录），另加 `propose_edit`（目标章候选稿）。工具为无状态实现，通过 `execute(args, context)` 接收不可变上下文；projectId、runId、目标章由后端注入，模型不可指定（PRD 5.3、5.4）。
- 成功条件强制"已通过 read_chapter 读取完整目标章"，否则以 `INSUFFICIENT_CONTEXT` 失败，不伪装成已完成检查。
- 三层预算：每次运行最多 8 次模型请求、12 次工具调用、30,000 码点工具结果累计；超限终止，不静默截断（PRD 9.2）。
- 工具输出统一 `{success, data, error}`，错误含 `retryableByModel`，区分"模型可修正参数重试"与"执行层不重试"。
- 同一响应内多个工具调用按 toolCallId 配对；缺失/重复 ID 判为无效模型响应，不执行一半再猜配对。

**面试可展开：** 为什么不用框架；工具为何按 list/read/search 拆成原子动作，设定为何批量读取（12 次工具预算）；toolCallId 配对与 `modelCallId + toolCallId` 本地定位；参数错误回传模型自纠 vs 网络/鉴权错误直接终态；截断的最终稿为何不能发布。

## 2. AI 只提建议，采纳走乐观并发控制

**业务需求：** AI 不能直接修改正式正文；任务期间用户可能手动保存了章节，旧建议不能覆盖新内容；重复采纳只能生效一次。

**技术实现：**
- 候选稿在运行中只存于助手消息/工具记录，仅在成功终态事务内发布为 `PENDING` 建议；失败、取消、超限不留下可采纳建议（PRD 5.5、8）。
- 采纳时校验所属任务成功、建议状态可采纳、目标章可访问，然后在一个短事务内：条件更新 `version = expectedVersion`、写入新 `tb_chapter_revision`、建议标记 `APPLIED` 并记录 `appliedVersion`（PRD 6.3）。
- 版本不匹配时不改正文、不写历史，建议标记 `CONFLICTED` 并**提交**，返回 409；不能因统一异常回滚而恢复为 PENDING。
- 手动保存与 AI 采纳共用同一套版本规则；内容无变化不增版本；版本不匹配即使内容相同也返回冲突（PRD 5.2）。
- 并发接受/拒绝只允许一方从 PENDING 转换，另一方得到已完成状态或状态冲突。

**面试可展开：** CONFLICTED 为何要提交而非回滚；乐观锁 vs 悲观锁的选择；AC-08（任务中手动保存后采纳旧建议）、AC-10（并发接受与拒绝）的处理。

## 3. 任务受理的并发准入：幂等键 + 作品活动槽 + 有界执行器

**业务需求：** 网络重试不能重复创建任务；同一作品同时只能有一个活动任务；不能无限创建线程或积压队列。

**技术实现：**
- 前端首次提交生成 `clientRequestId`，重试复用；后端以"用户范围 + clientRequestId"唯一约束去重，规范化摘要不同则返回 `IDEMPOTENCY_CONFLICT`（PRD 6.4）。
- `tb_project.activeRunId` 作为活动槽；受理时短事务内锁作品记录、校验槽位与章节版本、创建 run 并占槽，竞争请求只有一个成功（PRD 6.6）。
- 全局最多 2 个运行、8 个排队，容量不足返回 429 `RUN_CAPACITY_EXCEEDED`。
- 事务提交后执行器拒绝，必须转 `FAILED / SCHEDULING_FAILED`，提交失败事件并清理活动槽；不假装调度与事务天然原子（PRD 6.5）。
- 统一锁顺序：作品 → 运行/建议 → 章节；模型与网络调用一律在锁与事务之外。

**面试可展开：** PostgreSQL 唯一冲突后为何必须先回滚再新事务回读（ADR-001 2.4、PRD 6.8）；幂等命中为何优先于版本检查；为何不用 Redis 做分布式锁（ADR-002）。

## 4. 取消 / 超时 / 重启 / 数据库故障的唯一终态仲裁

**业务需求：** 任何失败、取消或并发冲突不得静默覆盖用户内容，也不能让任务永远显示"运行中"。

**技术实现：**
- `RunHandle(runId, executionId, future, cancelSignal, phase)`：先登记完整句柄再提交执行器，不能先运行后补登记（PRD 6.5）。
- 取消分"请求"与"确认"两步：RUNNING 下先写 `cancelRequested`，循环在下一安全点确认终态；成功提交与取消标记以原子状态转换仲裁，晚到的模型结果丢弃（PRD 6.1）。
- 注销按 `(runId, executionId)`；清理活动槽附加 `activeRunId = 本次 runId` 条件，防止旧任务 A 收尾误清新任务 B 的槽位。
- `Future.cancel(true)` / `Future.isDone()` 不作为工作线程已退出的证据；已启动任务的资源在线程真实退出时释放，未启动任务由取消路径释放，原子阶段转换保证只释放一次。
- 服务启动时先完成迁移和旧进程任务清理（`SERVICE_RESTARTED`），再开放受理；每个 run 记录 `processInstanceId`（PRD 6.7）。
- 排队/运行截止时间由周期扫描落实（初始 2 秒），不依赖"下次模型返回后再检查"。
- 持久化失败立即停止执行，登记待收尾；提交结果未知时先回读数据库，已提交的 SUCCEEDED/APPLIED 不能被补偿改为失败。

**面试可展开：** 执行身份校验解决的 ABA 类问题；为什么取消不承诺终止远端模型计算；数据库不可用时为何不能承诺立即落 FAILED。

## 5. SSE 进度推送 + 数据库事件游标断线恢复

**业务需求：** 刷新页面、断网重连后要恢复步骤记录，不漏不重；断线不能导致任务被取消；慢客户端不能拖慢 Agent。

**技术实现：**
- 不引入 Redis / MQ：事件与业务状态在同一短事务内分配单调递增 `seq` 并写入 `tb_agent_event`，同一 run 的分配串行化（PRD 7.4、ADR-003）。
- SSE 服务端每 500ms 跟读 `seq > cursor` 的已提交事件顺序推送，`id` 使用 seq；心跳 15 秒，不作为业务事件存储。
- 首次连接"先取任务快照，再以 afterSeq=lastEventSeq 订阅"；重连优先 `Last-Event-ID`，不允许跳到"当前最新序号"而遗漏事件。
- 客户端按 runId + seq 去重，旧快照不能覆盖已处理的新事件；终态后前端主动 close EventSource 再查详情。
- 发送失败只清理该连接与跟读任务，不取消 Agent；SSE 使用独立受限资源（全局 20 连接），不占用 Agent 工作线程。

**面试可展开：** 为什么选 SSE 而非 WebSocket / Socket.IO（ADR-003 4.4）；"先快照后订阅"如何避免漏事件；at-least-once 与客户端去重的关系；EventSource 不能加自定义头对未来鉴权的影响。

## 6. 正文字面搜索工具 + run 级版本视图

**业务需求：** Agent 要能查"主角在前文哪里说过不会游泳"，且不依赖嵌入模型；分页期间用户改了正文，不能出现"搜到一句话，读取时却没有"。

**技术实现：**
- `search_chapters`：单关键词区分大小写逐字匹配，范围 `BEFORE_TARGET`（默认）或 `ALL_CHAPTERS`，按"chapterOrder、行号、命中位置"稳定排序，不做相关性打分（PRD 5.9、ADR-004）。
- 首次搜索时在短一致读取事务内获取章节版本清单，与目标章 `baseVersion`、已读章首读版本合并为 run 专属 `chapterViewManifest` 落库；之后搜索、分页、`read_chapter` 均读同一不可变 `tb_chapter_revision`（ADR-005）。
- 游标由后端生成并绑定 runId、viewId、keyword、scope、最后位置；篡改或跨 run 使用返回 `INVALID_SEARCH_CURSOR`；`hasMore` 依据多取一条真实命中，不猜测。
- 行号、matchStart、matchEnd、snippetStart 按 Unicode 码点计数，避免 Java UTF-16 下表情符号导致偏移错误。
- 上限：视图最多 1,000 章、单次搜索 5 秒并受运行剩余时间限制、每页最多 20 命中、序列化 data 最多 12,000 码点；超限返回明确错误，不静默扫一半后声称完成。
- 扫描原文不进入模型上下文，只有实际返回片段计入 `contextManifest` 与工具文本预算。

**面试可展开：** 为什么是"每章固定版本"而非整书单一时刻快照；REPEATABLE READ 与默认 READ COMMITTED 的差别；字面搜索与后续混合检索（向量 + BM25 + RRF）的边界，未命中不等于无矛盾。

## 7. 模型消息与调用记录全量持久化（可审计）

**业务需求：** 任务详情要能解释"Agent 到底读了什么、模型说了什么"，出问题可排查，不能只剩"执行了 read_chapter"的摘要。

**技术实现：**
- `tb_agent_message`、`tb_agent_model_call`、`tb_agent_step` 三张表；助手消息与工具结果按 `modelCallId + toolCallId` 配对，本地 `toolExecutionId` 与提供方 ID 分开（PRD 5.6、8）。
- `contextManifest` 记录实际送入模型的完整章节 / 搜索片段、章节 ID/版本/片段位置、设定摘要哈希；扫描候选章或版本指针不等于模型已读。
- 落库顺序固定：先存调用记录与输入引用 → 请求模型（事务外）→ 存助手消息 → 执行工具 → 工具结果落库后才进入下一轮。
- 同一助手消息声明的所有工具结果完整对应后才允许下一次模型请求；取消/失败留下的未完成组标记 ABORTED，不伪造成功。
- 持久化失败立即停止执行，不发成功事件；密钥、鉴权头不落库；用量缺失留空，不估造 token 数。

**面试可展开：** "模型消息"与"产品事件/步骤展示"为何分层；为什么工具结果必须落库后才能用于下一轮。
