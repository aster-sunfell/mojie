# 新建与多建议修复验证

实现契约：[章节与设定建议](../design/setting-edit-proposals.md)。本次在隔离 PostgreSQL 数据库中测试，没有修改原作品内容，也未部署到原开发服务。

## 修复内容

- 两个现有 edit 工具支持显式 CREATE / UPDATE，无需新增独立的新建工具。CREATE 不传目标 ID 或版本；未知 ID 的 UPDATE 不会隐式转为新建。
- 每轮最多八份章节／设定建议，运行完成后原子发布全部草稿，对话分别展示、审阅和保存。
- 作者确认新建时写入完整 v1、AGENT 历史和建议关联；重复及并发保存返回相同正式对象。新章节在保存时追加。
- UPDATE 保留完整本轮读取和版本检查，旧建议不能覆盖新内容。拒绝、取消、运行失败不创建正式内容。
- 两次同工具同错误且未解决后停止工具循环；接近期限预留收尾请求。Chat Completions 无工具请求显式禁止工具调用，原生 DSML 正文作为协议错误处理。
- 供应商兼容：CREATE / UPDATE schema 使用扁平 properties / required，条件校验由服务端完成。

## 真实模型验证

模型为 SiliconFlow 的 deepseek-ai/DeepSeek-V3.2；隔离服务端口 18082、数据库 mojie_create_live_test。测试将故事构思与“为我创建 任务，世界观和写作约束”放在同一条消息中，不使用额外 Skill。最终证据：[真实模型记录](create-multiple-proposals-live-2026-10-12.json)。

最终运行 SUCCEEDED，用时 250.067 秒，7 次模型请求、6 次工具调用，产生 4 份 CREATE 草稿。保存前正式设定目录为空；任务、世界观和写作约束三份草稿分别为 251、413、343 字，逐份确认并重复确认后，实际目录恰有三项，全部为完整 v1，重复确认返回相同 ID。

模型还额外拟了一份 CHARACTER 人物稿，已拒绝，未创建正式对象。因此功能链路验收通过（verified=true），但严格“只生成请求的三份”检查未通过（strictRequestedScope=false）。提示词约束不能保证供应商完全遵守请求范围；这项模型行为限制保留在证据中，没有用重试掩盖。

中途未通过验收的尝试也保留证据：

- live-initial：oneOf schema 下供应商多次只生成 operation，随后返回原生工具标记。初次实现误将该正文记为 SUCCEEDED，但没有所需建议，因此 verified=false；后续增加协议校验。
- live-timeout：改为扁平 schema 后，过长正文生成超过单请求期限。
- live-protocol：三份请求草稿生成成功后，模型又创建了未请求的人物稿；最终无工具回复返回原生 DSML，整轮失败，正式设定及发布建议均为零。
- live-partial：显式禁用工具后成功返回普通正文并发布两份建议，协议修复有效；957 字的世界观生成耗尽第三份草稿的工具预算，未通过三份建议的验收。最终将初稿默认长度改为 200–350 字，先覆盖全部项目，避免无关章节目录读取。

这些结果支持工具能力和供应商协议／耗时问题共同影响原失败，不能仅凭一次截图归因于模型写作质量。修复不把错误协议输出伪装成成功，也不承诺供应商每次都在期限内完成。

## 应用

使用 Java 21 构建后端并构建前端。后端正常启动会自动执行 V15，保留旧建议为 UPDATE。原服务尚未重启，代码和构建产物已准备好。隔离验证服务已停止，测试数据库保留以便追查记录。
