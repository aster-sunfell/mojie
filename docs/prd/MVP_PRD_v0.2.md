## 1. 背景与产品目标

### 1.1 项目定位

构建一个辅助小说写作的 Web 工作台，让用户管理作品、章节和设定，并通过 Agent 检查当前章节中的设定一致性、提出修改建议。后端依据固定 OpenFic 源码理解并重实现工具调用循环、任务管理和受控写入，作为校招项目展示与 Agent 开发学习项目。学习重点是完整运行链路和异常处理，而不是仅调用框架封装的聊天接口。

第一版的目标不是自动创作整本小说，也不是通用聊天机器人。前端负责编辑、展示执行记录和确认修改；模型调用、工具权限、任务状态与数据写入由后端控制。

### 1.2 目标用户与核心场景

主要用户为管理自己作品的单个写作者。核心任务示例：“检查第二章中主角的行为是否符合人物设定，结合第一章内容提出修改建议，经我确认后再保存。”

系统允许只给出分析而不产生修改建议。缺少设定或证据时，应说明信息不足，不得声称已查阅未实际读取的内容。模型对文学合理性的判断只作为建议，不作为自动判定事实。

### 1.3 MVP 完成标准

**业务闭环：** 用户能新建作品与章节、维护设定、保存正文、发起任务、查看工具记录、接受或拒绝建议。

**数据安全：** 拒绝不改变正文；过期建议不能覆盖新版本；重复采纳只生效一次；失败或取消不产生可采纳的新建议。

**运行可见：** 页面刷新后可以恢复已保存的任务状态和执行记录；工具错误、超时、取消、服务中断均有明确结果。

**可验证性：** 固定的模拟模型测试覆盖关键状态与异常；真实模型演示能够完成端到端流程。不能只用演示截图代替验收。

**工程可追溯：** 第 2.2 节各参考项都有固定源码、处置结论、对应实现和测试证据；原项目与 Java 版本的行为差异可解释。

### 2.1 本版固定决策

**前端使用 React + TypeScript，选择性迁移基线前端。** 以可对照的上游工作副本梳理组件、业务 hooks、缓存、状态和初始化依赖，再迁入精简入口；不从截图重画整个产品，也不直接搬入完整前端后要求 Java 实现所有旧接口。正文采用受控纯文本编辑组件；Tiptap 富文本后置。原基线采用 React、Tiptap、TanStack Query、Zustand 等，可由依赖文件核对。[S22]

**后端使用 Java + Spring Boot，数据库使用 MySQL。** 以单体应用划分内容、Agent、工具、建议、事件等模块；不引入微服务或消息队列作为 MVP 依赖。

**一次任务固定一个目标章节。** Agent 可以只读其他章节与设定，但只能为目标章节生成至多一份可采纳建议。一个作品同时最多有一个排队中或运行中的任务。

**任务完成后再人工确认。** 用户采纳通过独立业务接口完成，不要求 Agent 长时间暂停并在审批后恢复执行。

**P0 推送步骤进度，不要求逐字输出。** 文本增量流式显示属于 P1；执行记录必须来自真实的模型与工具调用，不能用预置动画代替。

### 2.3 不随裁剪删除的工程底线

Controller 不承载整个 Agent Loop；工具不能直接绕过业务服务写正式正文；模型消息不能用前端步骤摘要代替；任务状态不能只放在线程或浏览器内存；前端断开不能结束任务；数据库保存失败不能被吞掉后继续显示成功。

框架和 SDK 可复用，但必须能通过本项目代码说明谁控制循环、权限、预算、取消和最终提交。避免为“工程完整”引入当前场景不需要的微服务、消息队列或多 Agent。

## 3. 端到端业务流程

### 3.1 主流程

1. 用户创建作品，添加章节和人物/世界观设定，在工作台编辑当前章节。
2. 正文有未保存改动时，用户先保存；保存成功后才允许发起 Agent 任务。
3. 前端提交目标章节、任务描述、当前章节版本和本次提交标识；后端校验后创建任务并立即返回 runId。
4. 后端固定目标章节的基准版本与正文快照，将任务交给受限执行器。Agent 按需调用工具查阅内容。
5. 前端展示真实的排队、执行、工具调用和完成状态。切换页面或断开连接不自动取消任务。
6. Agent 正常完成后，后端保存分析结果；有有效候选稿时，在同一提交过程中发布待确认建议。
7. 用户查看基准原文与建议稿，可整体接受或拒绝。接受时后端重新校验章节版本并完成事务写入。
8. 前端重新获取章节最新版，展示保存结果和新版本；任务与修改记录保留用于回看。

### 3.2 三种正常结果

**分析完成、无需修改：** 任务为 SUCCEEDED，展示分析结果，没有修改建议，不显示接受按钮。

**分析完成、有建议：** 任务为 SUCCEEDED，建议为 PENDING，正文尚未改变，用户可以接受或拒绝。

**用户拒绝：** 建议变为 REJECTED，任务仍为 SUCCEEDED，正文与章节版本均不变化。

### 3.3 关键异常结果

目标章节在任务生成建议后被修改，采纳时返回版本冲突；工具或模型失败时，任务最终进入 FAILED 并给出原因；取消生效后进入 CANCELLED，不发布可采纳建议；服务重启不续跑旧任务，未结束任务被标记为失败。

## 4. 前端信息架构与页面要求

### 4.1 页面与路由

| 编号 | 页面 / 入口 | 展示内容与主要操作 |
| --- | --- | --- |
| FE-01 | 作品列表 `/projects` | 作品名称、更新时间；新建、重命名、删除、进入作品 |
| FE-02 | 写作工作台 `/projects/:projectId` | 左侧章节导航，中间正文编辑，右侧 Agent 面板；选中章节后追加 `/chapters/:chapterId` |
| FE-03 | 工作台内的设定管理抽屉 | 分类、关键词筛选、设定列表、添加/编辑/删除 |
| FE-04 | Agent 面板内的任务记录 | 当前任务进度；历史任务列表；结果、工具步骤与错误 |
| FE-05 | 修改建议抽屉 | 基准原文、建议稿、修改理由、差异、接受/拒绝 |
| FE-06 | 章节历史抽屉 | 版本号、时间、来源、关联建议；只读查看版本正文 |

首版针对宽度不小于 1280px 的桌面浏览器验收。左侧导航和右侧 Agent 面板可折叠；不要求手机端达到相同工作台体验。主要动作必须有文字标签，不能只依赖图标。

### 4.2 FE-01：作品与章节导航

作品标题必填，1–80 个字符；章节标题必填，1–120 个字符。同名标题允许，关联一律以 ID 为准。新章节内容为空、初始版本为 1；默认按创建顺序展示，不做拖拽排序。

列表必须有加载态、空态和失败重试入口。空作品显示“新建第一章”，而不是空白编辑器。删除前进行二次确认；后端返回资源占用时，提示先结束任务或处理待确认建议。

URL 中的作品或章节不存在、已删除、关联不匹配时，展示不可访问提示与返回作品列表入口，不自动切换到其他作品。

### 4.3 FE-02：正文编辑与保存

编辑区展示章节标题、正文、字数、当前版本和保存状态。保存状态至少包括“已保存、未保存、保存中、保存失败、版本冲突”。支持保存按钮；在编辑区内支持 Ctrl/Cmd + S。

正文采用 UTF-8 纯文本，接口统一使用 LF 换行。不得自行 trim 正文或丢弃首尾空行。空正文可以手动保存；首版不支持 HTML、Markdown 渲染、图片或富文本节点。

**未保存保护：** 切换章节或离开工作台时，提供“保存后离开、放弃改动、取消”选择。浏览器关闭/刷新仅提供离开提醒；不承诺崩溃后找回未保存内容。

**保存冲突：** 请求携带 expectedVersion。发生冲突时保留本地编辑内容，不用服务器正文覆盖它；提供复制本地内容、加载服务器版本和取消操作。首版没有“强制覆盖”按钮。

**任务期间：** 用户可以继续手动编辑和保存正文，但界面提示当前任务基于启动时版本。后续建议可能因版本变化而无法直接采纳。

### 4.4 FE-03：设定管理

设定类型限定为 CHARACTER（人物）、WORLD（世界观）、RULE（写作约束）。每条包含标题和正文，不增加结构化人物关系图。标题 1–80 个字符，正文 1–2,000 个字符。

支持按类型与关键词查询，结果为空时明确显示“未找到设定”。删除需要确认。作品有排队中或运行中的任务时，设定的新增、修改和删除暂时禁用，并说明原因；后端也必须校验，不能只禁用前端按钮。

### 4.5 FE-04：Agent 面板与执行记录

任务输入为 1–2,000 个字符，可提供“检查人物设定一致性”等预填示例，但用户可编辑。提交前显示目标章节与版本；存在本地未保存正文时，必须先完成保存，不能悄悄丢弃改动或把未保存内容作为已存正文发送。

提交后显示 runId 对应的排队/运行状态。用户能看到工具名称、状态、可读参数摘要、结果摘要、耗时和错误原因；默认折叠长参数。不得展示密钥、服务端堆栈或模型内部推理文本。

运行中提供停止按钮；点击后显示“正在停止”，直到后端确认终态。按钮不能将本地 UI 直接改成已取消。任务失败可点击“重新运行”，但会创建新任务，不伪装成原任务恢复。

重新进入页面时，根据后端活动任务与历史任务查询恢复展示，不能只依赖浏览器内存中的 runId。SSE 断线时显示重连状态，必要时降级为定时查询；断线不等于任务失败。

### 4.6 FE-05：修改建议与采纳

对比固定展示“任务基准原文”和“建议稿”，采用只读双栏或行级差异高亮；首版只支持整体接受/拒绝，不允许直接修改建议稿。冲突后可复制建议稿，但不能绕过版本检查强制采纳。

必须展示基准版本、建议状态和修改理由。PENDING 且所属任务成功时才显示可用的接受/拒绝按钮；其他状态为只读。多个历史建议分别保留，采纳其中一份后其余旧版本建议仍须重新校验版本。

目标章节存在未保存编辑时，接受按钮禁用，提示先保存或放弃本地改动。采纳请求及刷新正文期间短暂锁定目标编辑器，避免采纳结果覆盖这段时间新输入的本地内容。

采纳成功后重新查询当前章节与历史列表，不直接把旧请求响应中的正文当成最新正文。采纳失败保留建议和当前编辑内容，错误信息应区分版本冲突、建议状态变化与网络失败。

### 4.7 FE-06：章节历史

每次真正改变正文的手动保存或 AI 采纳生成新版本。历史展示 CREATE、MANUAL、AGENT 来源，AI 版本可跳转到关联建议。首版只读查看，不提供一键回滚或分支合并。

### 4.8 前端迁移与状态约束

迁移顺序固定为“依赖梳理 → 精简入口 → 章节页面/hooks → Agent 面板 → 事件适配”。每次迁入组件时，同时列出它依赖的查询键、store、上下文 Provider 和 API；不能靠伪造成功响应维持旧初始化流程。上游写作 hooks 和应用入口可作为对应阅读点。[S19] [S21]

| 状态类别 | 本项目存放位置 | 更新规则 |
| --- | --- | --- |
| 作品、章节已保存版本、任务详情、建议 | TanStack Query 服务器缓存 | 以 Java 响应为准；写入成功后更新/失效对应查询 |
| 当前草稿、基准版本、dirty 标记 | 章节编辑器局部状态 | 不因 SSE 或后台 refetch 无条件重置 |
| 当前选中章节、抽屉与面板开关 | 路由 + 必要的局部状态/Zustand | 不存放唯一的任务终态或正式正文 |
| 运行事件展示 | `useRunEvents` 管理游标，更新任务投影 | 按 runId + seq 去重；卸载时清理连接/定时器 |
| 模型调用消息与真实执行状态 | 不由浏览器构建或决定 | 从后端查询；前端不能发起工具执行 |

保存时记录本次提交的正文快照；成功响应只能确认这份快照已保存。如果用户在请求期间继续输入，当前草稿仍为未保存，不能清空 dirty 或覆盖新输入。切换章节后迟到的响应只能更新对应章节缓存，不能写入当前编辑器。

后台重新获取服务器数据时，有本地草稿则保留草稿并提示服务器版本变化；无草稿时也应防止旧响应覆盖较新版本。采纳期间依照 FE-05 暂时锁定编辑器，采纳成功但后续刷新失败时，提示“已采纳，正文刷新失败”，不能伪装成采纳未发生。

Java 版本启动仅依赖本项目的健康/能力配置和内容 API。裁掉未使用的桌面桥接、原 Socket.IO 初始化、遥测和其他页面依赖；模型尚未配置时，内容编辑仍可使用，Agent 提交入口显示明确原因，不让整页一直停在加载中。

## 5. 后端业务模块与 Agent 能力

### 5.1 模块边界

| 模块 / 核心对象 | 职责 | 禁止混入的职责 |
| --- | --- | --- |
| Content / `ChapterService` | 作品、章节、设定、版本校验、历史保存 | 调用模型、决定工具顺序 |
| AgentRun / `AgentRunService` | 任务受理、幂等、并发准入、查询和状态转换 | 承担完整模型循环 |
| Runtime / `AgentRunner`、`RunRegistry` | 生命周期、运行句柄、取消、超时与收尾 | 直接修改正式正文 |
| Loop / `AgentLoop` | 请求模型、处理工具批次、回填结果、终止判定 | 知晓 HTTP Controller 或浏览器连接 |
| ModelAdapter / `ModelGateway` | 适配一个提供方的请求、工具调用、完成原因、用量及错误 | 自动执行工具、隐藏地再启动一套 Agent Loop |
| Tools / `AgentTool`、`ToolRegistry` | schema、上下文注入、参数与范围校验、调用业务服务 | 任意 SQL、Shell、网络或文件系统操作 |
| Context / `ContextBuilder` | 系统约束、消息组装、读取快照与上下文预算 | 根据 UI 步骤摘要拼造模型历史 |
| Trace / `RunTraceStore` | 有效消息、模型调用、工具结果和来源清单持久化 | 把密钥或完整正文打印到常规日志 |
| EditProposal / `EditProposalService` | 候选稿校验、建议发布、采纳/拒绝事务 | 自动跨章写入、自动合并 |
| RunEvent / `RunEventStore`、`RunEventStream` | 产品事件事务保存、按游标查询与 SSE 输出 | 以连接状态决定任务生死 |

模块运行在同一个 Java 应用内，不要求拆成多个 Maven 服务。模型通信可复用 SDK；使用 Spring AI 时也只使用模型适配能力，并核实未启用与本项目循环重复的自动工具执行。Agent 状态、权限、退出条件与最终提交由本项目显式控制。类名可调整，职责与测试边界不能消失。

数据流为 `Controller → AgentRunService → AgentRunner → AgentLoop → ModelGateway / ToolRegistry`。工具通过 Content 或 EditProposal 业务服务访问数据；运行过程通过 Trace 与 RunEvent 保存。上游参考关系见 REF-01 至 REF-10。

### 5.2 BE-01：内容与版本管理

手动保存和 AI 采纳必须共享同一套正文版本规则。更新需匹配 expectedVersion/baseVersion，并通过条件更新或等效并发控制验证；成功后版本加 1，同时新增对应历史记录。

正文和标题分别更新；修改标题不改变正文版本。正文内容无变化时不增加版本、不新增历史；版本已不匹配时，即使提交内容相同，也返回冲突，由客户端刷新后重试。

作品和章节使用逻辑删除。删除作品时，若存在活动任务或任意 PENDING 建议则拒绝；删除章节时，若该作品有活动任务或该章节有 PENDING 建议则拒绝。通过提示引导用户先停止任务或拒绝建议。已删除数据不在正常业务入口展示，历史数据不物理清除；首版不做恢复入口。

### 5.3 BE-02：运行上下文与读取范围

创建任务时，后端校验前端提交的目标章节版本，保存 targetChapterId、baseVersion 和 baseContent 快照。目标章节的 read_chapter 始终返回该任务的基准快照，使建议稿对应明确的原文。

作品 ID、用户范围、runId 和目标章节由后端注入工具上下文，模型不得自行指定或更改。读取其他章节时校验所属作品，并记录实际读取的版本；同一运行内重复读取同一章节返回首次读取的缓存结果。首版不承诺整部作品的全局快照一致性。

不同任务的会话不自动拼接。每个任务只使用当前任务描述、系统约束及本次工具结果。模型不可凭未读取的章节或设定声称已完成验证。

保存 `contextManifest`：实际读取的章节 ID/版本、设定 ID/内容摘要哈希、读取时间及对应工具执行 ID。重复读取快照可以缓存在内存中，其原始结果仍通过消息记录持久化。该清单用于解释本次分析依据，不是整部作品的事务快照。

采纳只强制检查目标章节版本。其他章节或设定在任务结束后可能变化，建议页面应展示分析基准及实际来源；本版不宣称“采纳时所有上下文仍是最新”，也不自动对所有来源做再次推理。后端可以强制验证资源范围和目标章已读取，但不能由此保证模型每一句文学判断或引用都正确；内容归因质量通过来源展示与真实模型评估核查。

Java 工具默认采用无运行状态的实现，通过 `execute(args, context)` 接收本次不可变上下文。注册表中的 schema/定义可以共享，但不能把 runId、projectId、messages 或当前数据库会话写进共享单例字段；两个作品并发运行时必须隔离。上游工具实例通过运行状态构造，本项目不把这种实例状态机械移植到共享 Bean 中。[S08] [S09]

### 5.4 BE-03：四个工具

| 工具 | 模型输入 | 结果与约束 |
| --- | --- | --- |
| list_chapters | cursor、limit（均可选） | 当前作品的章节 ID、标题、版本及分页信息；不返回整本正文 |
| read_chapter | chapterId | 章节正文与版本；目标章使用基准快照，其他章仅允许当前作品范围 |
| search_settings | keyword、type、limit | 标题/正文关键词匹配；类型可选；返回命中条目及总数，不做向量检索 |
| propose_chapter_update | chapterId、proposedContent、reason | 校验并产生候选稿；只允许目标章节；不写正式正文；不接受模型指定基准版本 |

Agent 必须先成功读取目标章节，才允许提交候选稿。候选稿不能为空、不得超过章节长度上限、不得与基准正文完全相同；已有一份有效候选稿时不再接受第二份。无修改必要时直接返回分析，不调用建议工具。修改理由必填且不超过 2,000 个 Unicode 码点。

工具输出使用统一结构 `{success, data, error}`；错误至少包含 `code`、可读 `message` 和 `retryableByModel`。其中 `retryableByModel` 只表示可修正参数后再调用，不表示执行层自动重试。每次调用生成本地 `toolExecutionId`；用 `modelCallId + toolCallId` 定位模型批次，不能仅假设提供方 ID 在所有任务中全局唯一。

设定搜索默认最多返回 5 条，稳定按 ID 排序；空关键词返回参数错误，无命中返回空集合而不是工具故障。工具参数错误、未知工具或跨作品请求返回结构化错误，可供模型修正，但仍消耗调用预算。越权结果不包含被拒绝资源的标题或正文。

单次工具结果过大时不截取半份正文冒充完整结果，而返回明确的结果过大错误；整个上下文累计预算已耗尽时终止运行。提供方返回缺失/重复的批内调用 ID、不可对应的协议结构时属于无效模型响应，不能执行一半后再猜测如何配对。

### 5.5 BE-04：Agent Loop

循环按“请求模型 → 校验返回 → 串行执行工具 → 将工具结果追加到消息 → 再请求模型”推进。模型决定读哪些章节与设定，不硬编码成固定的工具调用顺序。

同一响应中的多个工具调用按顺序处理，保留提供方的 toolCallId，工具结果必须与原调用对应。每轮模型请求前、每个工具执行前、发布最终结果前检查取消标记、截止时间和预算。

模型返回非空最终分析、完成原因有效、已成功读取目标章节且本次处理正常结束时，任务成功。对本产品的章节检查任务，未读目标章节便直接给出结论应以 `INSUFFICIENT_CONTEXT` 失败，而不是伪装成已完成检查。若有有效候选稿，则在任务成功提交时发布一条 PENDING 建议；候选稿验证完成不代表已经发布。后续失败、取消或达到上限时不得留下可采纳的新建议。

首版不做隐式无限重试。工具参数错误可回传模型自行修正；网络、鉴权、无效模型响应、长度截断或预算耗尽应产生明确终态。检测到被截断的最终稿不得当作完整建议发布。

### 5.6 BE-09：模型消息与调用记录必须持久化

参考 REF-07 保留“模型消息”和“产品事件/步骤展示”分层，不能只有“执行了 read_chapter”的摘要。上游的消息加载器会处理工具调用/结果的对应关系，持久化器处理执行产生的消息；本项目借鉴这一职责，不移植其完整会话与检查点模型。[S11] [S12]

每次运行至少保存以下信息：

| 数据 | 必须保留 | 不应保存/展示 |
| --- | --- | --- |
| 初始输入 | 用户指令、实际系统约束快照、提示词版本/哈希、工具 schema 版本/哈希 | 密钥、鉴权请求头 |
| 助手消息 | 实际文本、声明的工具调用 ID/名称/参数、所属模型调用序号 | 不要求采集或展示模型隐藏推理 |
| 工具消息 | 发给模型的真实结果或结构化错误、对应调用 ID、工具执行 ID | 不能只保留前端摘要代替真实结果 |
| 模型调用记录 | 开始/结束、输入消息序号范围或有序 ID、模型标识、配置快照、完成原因、错误、用量（可空） | 不把估计 token 数或未返回的用量写成真实计费数据 |
| 未完成链路 | 已保存的消息、未完成工具的 ABORTED 状态、运行失败原因 | 不伪造“工具已成功”补齐审计记录 |

固定上限内的完整工具结果保存在受控业务表，普通日志只输出标识、摘要和错误。调试读取接口仅在本地开发模式开放；前端常规任务详情不返回完整系统提示、原始请求头或无关提供方元数据。

每轮调用模型前先保存调用记录和输入消息引用；收到可处理响应后，先保存助手消息，再执行工具；工具结果持久化成功后才用于下一轮。状态、相关步骤和业务事件应在相应短事务中一致提交。

同一助手消息声明的所有工具结果完整对应之后，才允许发起下一次模型请求。取消或失败导致的未完成组保留用于排查，但不拿它继续调用模型。本版不从历史任务自动恢复执行，也不把旧任务消息拼接到新的“重新运行”。

消息/调用记录无法落库时，停止进一步模型或工具执行，不继续生成成功建议。数据库整体不可用时，不能承诺立即落下 FAILED；应停止执行、报警并使健康检查失败，待数据库恢复后由状态清理流程补记失败（见 6.7）。**没有已提交的成功结果，就不能向前端发成功事件。**

### 5.7 BE-10：单一模型适配边界

`ModelGateway` 输入是已构建的消息、工具定义和调用配置；输出至少为 `text`、`toolCalls`、`finishReason`、`usage`、提供方请求标识（如有）。它不执行工具、不决定项目权限、不更新正文。

首版只接入一个经 M0/M2 验证的、支持结构化工具调用的文本模型。提供方、实际模型 ID、API 形态、SDK/BOM 版本与必要协议字段写入配置说明；不能仅凭“兼容某接口”宣称所有模型都可用。配置、工具定义和系统约束在一个 run 内固定。

本版不要求模型响应逐字推送，也不要求自己实现流式工具参数拼接。优先使用完整响应；所选 SDK 只能提供流时，适配层必须完整聚合并验证响应后再执行工具，不能边收到半段参数边执行。

上游模型调用层具有错误分类、超时和重试逻辑；本版保留错误分类和单一调用入口，**P0 设为一次尝试，不做自动网络重试**。确认 SDK 默认重试已关闭，避免循环层、SDK 层重复重试。鉴权、配额、网络、超时、上下文超限、空响应和截断必须区分记录。[S07]

所选模型要求回传的必要协议元数据由适配器明确处理；不能随意丢字段后仍宣称兼容。模型拒绝或信息不足应如实呈现，不把这些情况包装成成功修改。预算检查包括完整消息、schema 和输出预留，字符限制不能替代模型上下文限制。

### 5.8 一次运行的最小执行顺序

```text
受理：校验 → 幂等命中或创建 run/基准快照/输入记录/queued 事件 → 提交
调度：登记本次 RunHandle → 交给有界执行器 → 校验状态 → 标记 RUNNING

循环：
  检查取消、截止时间、预算
  → 构建并校验输入消息
  → 保存模型调用开始记录
  → 请求模型（事务之外）
  → 验证、保存助手消息和调用结果
  → 有工具：逐个校验、执行、保存结果，再进入下一轮
  → 无工具：校验最终分析，进入成功提交

提交：
  同一短事务：确认仍可完成 → 保存结果 → 发布可选建议 → 成功状态和事件
收尾：
  按执行身份注销句柄；只清理属于自己的活动占位；资源实际退出后释放容量
```

四个工具的顺序由模型决定，不按固定脚本排列；上述运行阶段的安全检查和提交规则由后端决定，不能交给模型自行选择。

## 6. 状态、事务、幂等与异常规则

### 6.1 BE-05：任务状态

| 状态 | 含义 | 允许的后续状态 |
| --- | --- | --- |
| QUEUED | 已持久化，等待执行 | RUNNING、CANCELLED、FAILED |
| RUNNING | 正在请求模型或执行工具 | SUCCEEDED、FAILED、CANCELLED |
| SUCCEEDED | 分析结束，可能有待确认建议 | 无，终态不可回退 |
| FAILED | 失败、超时、预算耗尽或服务中断 | 无，重新执行创建新任务 |
| CANCELLED | 后端已确认取消生效 | 无，重新执行创建新任务 |

取消请求与取消完成分开：RUNNING 下设置 cancelRequested 标记，前端显示“正在停止”；只有后端终止处理后才显示 CANCELLED。队列中的任务可直接取消。

取消与成功发布必须以受控原子状态转换仲裁：成功先提交，则取消返回现有成功状态；取消标记先被确认写入，则后续处理不得发布成功结果或待确认建议。晚到的模型结果必须丢弃。

### 6.2 BE-06：修改建议状态

| 状态 | 含义 | 后续动作 |
| --- | --- | --- |
| PENDING | 待用户确认，正文未改变 | 接受 → APPLIED；拒绝 → REJECTED；采纳时版本不符 → CONFLICTED |
| APPLIED | 已保存为章节新版本 | 重复接受返回既有结果，不再写入 |
| REJECTED | 用户已拒绝 | 不可重新接受；需要时重新运行 |
| CONFLICTED | 已确认基准版本过期 | 不可强制接受；保留只读与复制能力 |

任务状态与建议状态独立。采纳、拒绝或冲突不回改原任务的 SUCCEEDED 状态。

### 6.3 BE-07：采纳事务

接受建议时，后端验证所属任务成功、建议状态可采纳、目标章节仍可访问，随后在一个短事务内完成：校验并更新章节版本、写入新章节历史、把建议标记为 APPLIED 并保存 appliedVersion。

基准版本不匹配时，不更新章节、不新增章节历史，将建议标记为 CONFLICTED 并返回 409。冲突状态应被提交保存，不能因为统一异常回滚而意外恢复为 PENDING。

拒绝仅修改建议状态。正文与版本保持不变。采纳与拒绝并发时只允许一方从 PENDING 成功转换，另一方得到已完成状态或状态冲突，不得出现“已拒绝但正文已被该建议写入”。

模型调用不得包含在长时间数据库事务中；创建任务、保存步骤、更新状态、发布建议与采纳分别使用短事务。事件与相应业务状态一起提交，避免 UI 已显示成功但业务未保存。

### 6.4 BE-08：重复提交、队列与进程中断

前端每次首次提交生成 clientRequestId；因超时或网络错误重试同一次提交必须复用该值。后端以用户范围 + clientRequestId 唯一约束去重，同一规范化请求返回原 runId，内容不同返回 IDEMPOTENCY_CONFLICT。摘要至少覆盖 projectId、targetChapterId、expectedVersion 和 instruction；不包含服务端生成时间等易变字段。

幂等记录命中优先于重新检查当前章节版本，保证首次请求已成功而响应丢失后仍能找回原任务。“重新运行”使用新的 clientRequestId，不能复用旧键。前端对响应未知的提交保留原请求和原键，完成状态核实前不能把一次网络重试转换成新任务。

一个作品最多存在一个 QUEUED/RUNNING 任务；该约束需在后端原子校验，不能仅查询后判断。全局采用有界线程与队列，容量不足返回 429，不得无限创建线程或积压任务。创建记录后若调度失败，应转为 FAILED，不能永久留在 QUEUED。

服务启动时，将前一次进程遗留的 QUEUED/RUNNING 任务置为 FAILED，错误码为 SERVICE_RESTARTED，并产生相应事件。已有成功建议和历史不受影响；遗留的模型调用/工具步骤同步收尾，不继续显示 RUNNING。首版不恢复未完成的内存执行上下文。

### 6.5 BE-11：运行身份、登记与有界调度的默认实现

上游 `_launch_task` 在任务进入运行器前登记任务，注册表的注销和定向取消检查任务对象身份；本项目保留这些行为，不照抄 Python 异步实现。[S24] [S05]

Java 首版采用 `RunHandle(runId, executionId, future, cancelSignal, phase)`、线程安全注册表和有界执行器。`executionId` 标识本次实际执行实例；`future` 的完成状态不能替代数据库业务状态。

| 时点 | 必须发生的行为 |
| --- | --- |
| 受理前 | 先尝试命中幂等记录；容量满且尚未持久化任务时返回 429 |
| 创建任务 | 事务内固定基准快照，创建 QUEUED、输入与事件记录，并占用作品活动槽 |
| 交给线程前 | 先登记完整运行句柄，再提交执行器；可以预构造 FutureTask，但不能先运行后补登记 |
| 工作线程入口 | 从已提交任务检查取消标记和 QUEUED 状态；只能成功领取一次，之后转 RUNNING |
| 排队取消 | 原子阻止尚未开始的执行并回收排队资源；不能等待一个永远不会运行的 finally |
| 运行取消 | 先提交取消请求，再尝试中断本地调用；循环在下一安全点确认终态 |
| 执行退出 | 按 `(runId, executionId)` 注销；清理作品槽时附加 `activeRunId = 本次 runId` 条件 |
| 晚到结果 | 重新检查运行状态；终态后不得发布结果、恢复运行或产生待确认建议 |

调度与事务不能假装天然原子。事务提交后若执行器拒绝，必须将该 run 标记为 `FAILED / SCHEDULING_FAILED`，提交失败事件并清理活动槽。任务资源已经存在时，创建接口返回 202 和实际状态，幂等重试返回同一 run；不得一面保留 QUEUED，一面仅抛出一个 HTTP 错误。

取消、执行器拒绝、任务自然结束等路径必须共用幂等的清理逻辑，但要区分“尚未启动”和“实际已启动”。**`Future.cancel(true)` 或 `Future.isDone()` 不能单独作为正在运行的工作线程已退出的证据。** 已启动任务的并发资源应在本地请求/工作线程真实退出时释放；未启动任务由取消路径释放；两者以原子阶段转换保证只释放一次。

模型远端请求不一定因本地取消立即停止计算或计费。产品只承诺取消确认后不再执行后续业务动作、不发布建议；不承诺强制终止远端计算。传输超时和总运行截止时间仍必须生效。

### 6.6 BE-12：作品活动槽与数据库短事务

默认在 `project` 保存可空 `activeRunId`，不把内存 Map 当作唯一并发控制。受理任务时，在短事务中锁定作品记录，校验活动槽、章节版本及资源状态，创建 run 并写入活动槽。竞争请求只能有一个成功。

删除作品/章节、变更设定，以及运行期间需冻结的目录结构操作，都使用同一个作品级短事务校验，避免“先查无活动任务、随后另一个请求启动任务、再执行删除”的竞争。任务活动期间禁止新增/删除/重命名章节等目录结构操作；正文手动保存继续允许，并使用版本条件更新。

任务完成或取消清理活动槽时，只能清理仍指向自己的 `activeRunId`。新任务 B 已占位时，旧任务 A 的收尾不得将其清空。内存注册表与数据库槽各自做身份校验，不能只保护其中之一。

涉及多行锁的业务操作统一锁顺序：需要作品锁时先作品，再运行/建议，最后章节；模型和网络调用全部在锁与事务之外。具体 SQL、唯一约束和异常回滚方式在 M1/M2 的详细设计中补齐，并以 MySQL 集成测试确认，而不是靠前端禁用按钮保证。

创建任务的幂等唯一键可能与作品槽竞争同时发生。事务内再次核对幂等键；发生唯一键冲突后回读已提交记录，释放本请求的准入资源，不能额外创建任务或泄漏容量。

### 6.7 BE-13：超时、数据库故障和进程中断

模型连接/响应有传输超时，运行有独立总截止时间。排队超时和运行超时通过周期检查落实，不能只在“下一次模型返回后”检查，否则长时间阻塞时界面会一直显示运行中。周期检查不得绕过第 6.1 节的唯一终态仲裁。

服务启动时，先完成迁移和旧进程任务清理，再开放任务受理；每个 run 记录 `processInstanceId`。只在确认单实例、旧进程不再运行的部署边界内清理旧任务，本版不支持多实例滚动部署。

消息、结果或终态提交失败后，立即停止继续执行，并在本进程登记待收尾任务；数据库恢复后重试短事务收尾，不重放模型调用。若提交结果未知，先回读数据库：已提交的 SUCCEEDED/APPLIED 不能被后续补偿改为失败；确认未成功的未结束任务才补记 `PERSISTENCE_ERROR`。进程已经退出时由下次启动的 `SERVICE_RESTARTED` 清理处理。

常规正文保存、建议采纳、消息记录、终态发布都不得捕获数据库异常后返回假成功。数据库不可用期间，健康检查反映异常并拒绝新任务；不能承诺存储故障时仍即时写下最终状态。

## 7. API 与前后端联调契约

### 7.1 通用约定

API 使用 `/api/v1` 前缀；ID 以字符串传输，版本号使用正整数，时间采用带时区的 ISO 8601 格式。正常响应使用 data 包装；错误响应包含 code、message、requestId、details。requestId 为后端排查标识，与业务幂等字段 clientRequestId 不同。

前端仅展示可读错误，服务端堆栈保留在脱敏日志中。路径或请求同时指定作品与子资源时，必须校验关联；工具读取本次任务作品之外的 ID 时返回 RESOURCE_NOT_FOUND，避免越过任务范围。

### 7.2 内容接口

| 方法与路径（省略前缀） | 用途 | 关键输入 / 输出 |
| --- | --- | --- |
| GET /projects | 作品列表 | 游标分页；返回名称、更新时间 |
| GET /projects/{id} | 作品详情 | 供直接进入工作台和页面刷新使用 |
| POST /projects | 创建作品 | title |
| PATCH /projects/{id} | 重命名作品 | title |
| DELETE /projects/{id} | 删除作品 | 逻辑删除；资源占用返回 409 |
| GET /projects/{id}/chapters | 章节列表 | 游标分页；ID、标题、版本 |
| POST /projects/{id}/chapters | 创建空章节 | title；返回初始版本 |
| GET /chapters/{id} | 章节详情 | projectId、title、content、version |
| PATCH /chapters/{id} | 修改章节标题 | title；不修改正文版本 |
| PUT /chapters/{id}/content | 保存正文 | content、expectedVersion；返回新版本 |
| DELETE /chapters/{id} | 删除章节 | 逻辑删除；活动任务/待确认建议校验 |
| GET /projects/{id}/settings | 查询设定 | keyword、type、cursor、limit |
| POST /projects/{id}/settings | 添加设定 | type、title、content |
| PATCH /settings/{id} | 修改设定 | type、title、content；任务期间禁止 |
| DELETE /settings/{id} | 删除设定 | 任务期间禁止 |
| GET /chapters/{id}/revisions | 历史列表 | 游标分页；版本、来源、时间 |
| GET /chapters/{id}/revisions/{version} | 历史详情 | 只读版本正文 |

### 7.3 任务与建议接口

| 方法与路径（省略前缀） | 用途 | 关键行为 |
| --- | --- | --- |
| POST /agent/runs | 创建任务 | 返回 202；不等待模型完成 |
| GET /agent/runs | 查询活动/历史任务 | projectId 必填；chapterId、status、cursor 可选 |
| GET /agent/runs/{id} | 状态与结果 | 状态、步骤、结果、proposalId、lastEventSeq |
| GET /agent/runs/{id}/events | SSE 订阅 | afterSeq 可选；重连支持 Last-Event-ID |
| GET /agent/runs/{id}/trace | 开发排查 | 仅本地开发模式；返回受控消息、调用与来源清单，不返回密钥 |
| POST /agent/runs/{id}/cancel | 请求取消 | 返回当前状态与 cancelRequested |
| GET /edit-proposals/{id} | 查看建议 | 基准原文、建议稿、理由、状态、基准版本 |
| POST /edit-proposals/{id}/accept | 采纳建议 | 不接收正文；返回状态和 appliedVersion |
| POST /edit-proposals/{id}/reject | 拒绝建议 | 幂等返回拒绝结果；已采纳时返回冲突 |

另提供 `GET /health` 与 `GET /system/capabilities`（与本节表格一致，均省略 `/api/v1` 前缀）：前者反映服务/数据库可用性，后者返回本版长度限制、Agent 是否配置就绪等公开能力。健康检查不得每次调用付费模型；模型未配置不阻止内容编辑。返回字段在 OpenAPI 中固定。

创建任务的请求示例：

```json
{
  "projectId": "p_001",
  "targetChapterId": "c_002",
  "expectedVersion": 5,
  "instruction": "检查当前章节是否符合人物设定，并提出修改建议。",
  "clientRequestId": "58e9b181-745c-4e52-a475-8b88558201b5"
}
```

建议采纳接口不接收 proposedContent、baseVersion 或目标章节 ID，以数据库中的建议记录为准。重复接受 APPLIED 建议返回既有 appliedVersion；前端随后重新读取当前章节，避免把历史版本当作当前正文。

### 7.4 事件与断线恢复

上游产品事件转换和连接管理作为职责参考；下述数据库游标协议为本项目定义，不兼容原 Socket.IO。[S13] [S14] [S20]

P0 事件为 `run.queued`、`run.started`、`model.started`、`model.finished`、`tool.started`、`tool.finished`、`run.succeeded`、`run.failed`、`run.cancelled`。失败的模型/工具调用通过 finished 的状态和错误字段表达；不要只用 UI 颜色暗示失败。

业务事件必须持久化，带有同一 run 内单调递增且唯一的 `seq`。SSE 的 `id` 使用该序号；`data` 包含 `schemaVersion`、runId、seq、type、occurredAt、payload。心跳不作为业务事件存储。

```text
id: 4
event: tool.finished
data: {"schemaVersion":1,"runId":"r_001","seq":4,"type":"tool.finished","occurredAt":"2026-09-22T10:00:00Z","payload":{"toolExecutionId":"te_001","status":"SUCCEEDED"}}
```

**P0 选用数据库游标跟读，避免同时维护两套事件真相。** RunEventStream 以受限周期读取已提交的 `seq > cursor` 事件，按序发送 SSE；这仍是 SSE 推送，数据库跟读只是服务端内部实现。当前低并发场景不要求消息队列或内存实时发布系统。

| 环节 | 契约 |
| --- | --- |
| 事件分配 | 在更新 run/步骤的短事务中分配 seq、更新 lastEventSeq 并插入事件；同一 run 的分配串行化 |
| 任务快照 | 状态、步骤、结果与 lastEventSeq 来自一致的数据库读取快照，避免拿旧状态配新序号 |
| 首次连接 | 先 GET 任务快照，再以 afterSeq=lastEventSeq 连接；期间产生的事件从数据库补发 |
| 重连 | 存在合法 Last-Event-ID 时优先使用它，否则用 afterSeq；不能取“现在的最新序号”跳过遗漏 |
| 客户端处理 | 按 runId + seq 去重；旧快照不能覆盖已处理的新事件；收到未知 schema 版本时降级查询 |
| 发送失败 | 只清理该 SSE 连接与跟读任务，不取消 Agent；慢客户端不得阻塞模型工作线程 |
| 终态 | 发完已提交的终态事件后关闭订阅；前端再查一次详情并停止重连/轮询 |
| 游标非法 | 非法值或超出本 run 最新序号返回明确错误，前端重新获取快照；不静默遗漏事件 |

本版不清理运行期业务事件，因此不实现事件保留期过期后的增量恢复。事件用于展示与排查，不声称实现完整事件溯源或“恰好一次传输”；客户端必须容忍重复。

SSE 持续失败时，前端每 2 秒查询任务快照；已知终态后停止。重新载入只需恢复步骤、分析与建议，不要求回放逐字输出。用户后续采纳/拒绝发生在 run 终态之后，依赖建议接口结果和相关查询失效刷新，不依赖已关闭的运行事件流。

反向代理需关闭该路径的响应缓冲并允许长连接；数据库跟读、心跳和连接关闭均使用独立的受限资源，不能占用 Agent 的两个工作线程。

### 7.5 错误码与界面行为

| HTTP / 业务码 | 场景 | 前端行为 |
| --- | --- | --- |
| 400 VALIDATION_ERROR | 输入为空、长度超限、格式非法 | 定位字段，保留用户输入 |
| 404 RESOURCE_NOT_FOUND | 不存在、已删除或不在允许范围 | 停止相关操作，提供返回入口 |
| 409 VERSION_CONFLICT | 保存或采纳时版本过期 | 保留本地内容/建议，提示刷新与重新处理 |
| 409 RESOURCE_BUSY | 同作品已有任务或删除被占用 | 指向活动任务或待确认建议 |
| 409 PROPOSAL_STATE_CONFLICT | 采纳/拒绝遇到其他终态 | 刷新建议状态，不反复提交 |
| 409 IDEMPOTENCY_CONFLICT | 同一提交标识对应不同请求 | 提示重新发起，不覆盖原任务 |
| 429 RUN_CAPACITY_EXCEEDED | 执行队列已满 | 保留输入，允许稍后重试 |
| 429 STREAM_CAPACITY_EXCEEDED | SSE 连接数达到上限 | 保留任务展示，退避重连或降级查询；不重复创建任务 |
| 任务错误 MODEL_ERROR / INVALID_MODEL_RESPONSE | 提供方失败或响应不可处理 | 显示任务失败，可新建任务重试 |
| 任务错误 RUN_TIMEOUT / LIMIT_EXCEEDED | 时间、轮数、工具或上下文预算耗尽 | 显示具体触发限制，不发布新建议 |
| 任务错误 SERVICE_RESTARTED | 进程重启中断 | 提示原任务未继续执行，可重新运行 |
| 任务错误 SCHEDULING_FAILED | 已创建任务但调度失败 | 显示失败；不保留虚假的排队状态 |
| 任务错误 PERSISTENCE_ERROR | 消息或结果持久化失败 | 显示失败或状态暂不可确认；恢复后重新查询 |
| 任务错误 INSUFFICIENT_CONTEXT | 未读取目标章节便给出最终结论 | 显示检查未完成，不展示可采纳建议 |
| 503 SERVICE_UNAVAILABLE | 数据库不可用或服务尚未就绪 | 保留本地输入，禁止把未知结果当成成功 |

模型执行失败通常通过任务状态查询与事件返回，不把一个已经返回 202 的创建请求“改成 HTTP 500”。

## 8. 逻辑数据模型与一致性约束

本节定义前后端可观察的持久化需求，不替代后续 DDL 与 OpenAPI。业务字段可在详细设计中补充，但不能省略版本、幂等与审计约束。

| 实体 | 最少保存的信息 | 核心约束 |
| --- | --- | --- |
| project | ID、用户范围、名称、activeRunId、创建/更新时间、删除标记 | 活动槽与任务创建原子更新；正常访问过滤删除标记 |
| chapter | ID、projectId、标题、正文、version、删除标记 | 正文更新必须检查版本 |
| chapter_revision | chapterId、version、完整正文、来源、proposalId、时间 | chapterId + version 唯一 |
| setting | ID、projectId、type、title、content、时间、删除标记 | 工具查询必须限制作品范围 |
| agent_run | 目标章、基准快照、指令、状态、取消标记、幂等键/摘要、结果、错误、时间、配置/提示词/schema 快照、contextManifest、processInstanceId、lastEventSeq | 用户范围 + clientRequestId 唯一；终态不可回退 |
| agent_message | runId、messageSeq、role、content、toolCalls/toolCallId、modelCallId、状态及必要协议字段 | runId + messageSeq 唯一；实际输入/输出可定位，工具组可配对 |
| agent_model_call | runId、callIndex、有序输入消息引用、配置哈希、请求标识、状态、完成原因、错误、耗时、用量 | runId + callIndex 唯一；无自动隐藏调用 |
| agent_step | toolExecutionId、runId、modelCallId、toolCallId、工具名、参数/结果引用、展示摘要、状态、耗时 | modelCallId + toolCallId 唯一；本地执行 ID 与提供方 ID 分开 |
| agent_event | runId、seq、类型、payload、时间 | runId + seq 唯一，与业务状态一致提交 |
| edit_proposal | runId、目标章、基准版本/正文、建议稿、理由、状态、appliedVersion | runId 唯一；一次运行至多一条已发布建议 |

初始章节创建即生成版本 1 的 CREATE 历史；每次有效保存保存新版本完整正文，暂不做增量存储。AI 来源历史中的 proposalId 需要唯一性保护，防止同一建议生成多次修改记录。

任务记录模型名称、模型请求次数、工具次数与耗时；提供方返回 token 用量时记录，缺失则留空，不估造成真实值。以上为 10 个逻辑实体，可在详细设计中合理调整物理表，但不能删掉消息配对、幂等、版本与审计要求。

内存消息是运行中的工作副本，已完成的协议消息与调用记录必须写入数据库。系统提示与 schema 快照可按哈希引用仓库中的不可变版本或受控存储，但仅保存一个未来可能无法解析的哈希不算完整记录。

新建章节生成版本 1 历史；建议候选阶段不创建可采纳的 edit_proposal。候选内容可留在本次助手消息/工具记录中，仅在成功终态事务内发布。终态任务的未结束模型调用或工具步骤应标记为 ABORTED/FAILED，不能永久显示运行中。

## 9. 非功能要求与初始配置

### 9.1 建议技术基线

前端：React、TypeScript、React Router、TanStack Query；工作台局部状态按需要使用 Zustand，UI 选择性保留基线的基础组件。网络访问统一收敛在 API/事件层，不在各组件中散落请求逻辑。保留上游工作副本及其锁文件；本项目精简后的依赖另有自己的锁文件，不以“依赖上游”作为不锁版本的理由。

后端：Java、Spring Boot MVC、MySQL、MyBatis、数据库迁移工具、Maven。模型适配、工具循环、业务服务应可独立测试；P0 不引入分布式消息队列、Redis 或通用图编排框架。JDK、Spring Boot BOM、MySQL、SDK 与迁移工具的精确版本在 M0/M1 的环境清单中锁定，并经实际构建确认；这里不凭空指定未经验证的版本组合。

部署：浏览器通过同一源访问前端和 `/api`，后端密钥通过环境变量或服务端配置注入。模型提供方与模型名称由服务端配置，首版不做前端配置密钥页面。

### 9.2 初始限制

下列数值是控制 MVP 范围的初始配置，不是已实测的性能结论。实现后可根据真实模型和测试结果调整，变更需同步前端提示与验收用例。

| 项目 | 初始值 / 规则 |
| --- | --- |
| 单章正文与建议稿 | 最多 6,000 个 Unicode 码点；手动正文可为空，建议稿不可为空 |
| 任务描述 / 单条设定正文 | 最多 2,000 个 Unicode 码点 |
| 单次设定工具结果 | 最多 5 条；不默默截断单条正文 |
| 单次目录工具结果 | 默认 20 条，最大 50 条，支持游标继续读取 |
| 每次运行模型请求 | 最多 8 次；参数纠错也计入 |
| 每次运行工具调用 | 最多 12 次；失败调用也计入 |
| 工具结果累计文本预算 | 最多 30,000 个 Unicode 码点，同时校验完整模型输入与输出预留；累计超限终止，不静默截断 |
| 模型连接 / 请求 / 运行超时 | 连接最多 10 秒；单次请求总计最多 60 秒；开始运行后总计 180 秒；均不超过剩余截止时间 |
| 单轮模型尝试次数 | 1；SDK 自动重试关闭，所有尝试计入调用记录 |
| 超时扫描 | 初始每 2 秒检查排队/运行截止时间；模拟测试可使用可控时钟 |
| 排队等待上限 | 60 秒；超过后转 FAILED，错误为 RUN_TIMEOUT |
| 并发与队列 | 全局最多 2 个运行、8 个排队；每作品最多 1 个活动任务 |
| SSE 跟读 / 心跳 / 查询降级 | 跟读初始 500 毫秒；心跳 15 秒；客户端降级轮询 2 秒；终态后停止 |
| SSE 资源 | 跟读与发送使用独立受限资源；初始全局最多 20 条连接，单连接每批最多 100 条事件 |

输入预算与输出预算需匹配所选模型，不能仅凭字符数断言适配。M0/M2 必须用接近 6,000 码点的正文验证完整建议稿能在所选输出预算内返回；不通过时调整公开长度上限或模型配置，并同步验收，不能偷偷截短正文。模型报告超长、截断或工具参数不完整时不发布建议。正文计数前统一 CRLF 为 LF，其余字符与空行保持不变。

### 9.3 安全与可靠性底线

默认本地单用户模式，使用服务端固定的 DEMO_OWNER 作为用户范围，浏览器不能指定身份；服务仅对本机开放。这不是完整鉴权系统。公开演示前必须增加受保护的访问入口、调用额度限制及必要的浏览器请求保护；未实现前不得把无鉴权写接口直接暴露到公网。

模型密钥仅保留在后端；日志、任务记录、SSE 与前端构建产物不得包含密钥。浏览器写请求只允许明确配置的可信来源，不配置任意来源跨域放行；模型地址由服务端配置，不能由工具参数指定。前端将模型文本当作不可信纯文本展示，禁止将其直接作为 HTML 执行。

工具没有任意代码、网络、数据库或文件操作权限。章节或设定中的“忽略规则”“读取其他作品”等文字只是业务数据；越权行为由后端工具校验拦截，不能仅依赖提示词。

普通列表、保存与创建任务请求不能等待模型完成。开发验收需记录测试环境；以 100 章、200 条设定的固定数据集连续请求 20 次，非模型接口至少 19 次在 1 秒内完成作为初始目标。模型生成耗时不计入该指标。

### 9.4 测试与日志

模拟模型客户端应支持按预设序列返回工具调用、参数错误、最终回答、异常与超时，用于稳定验证循环。版本冲突、并发采纳和事务回滚应使用与生产一致的 MySQL 行为进行集成测试。

日志以 requestId、runId、stepId 关联，记录开始/结束、耗时、错误码和状态变化；默认不打印完整正文、设定、请求密钥或模型内部推理。需要排查时优先使用最小化、脱敏的测试数据。

| AC-28 | 获取快照后立刻产生事件；发送中断；重复重连；旧快照迟到 | 数据库跟读补发已提交事件；去重且不回退；快照与 lastEventSeq 一致 |
| AC-29 | 保存期间继续输入、切换章节；后台 refetch；采纳成功但正文刷新失败 | 不覆盖新输入/其他章节；状态文案准确；不会因刷新失败重复写正文 |
| AC-30 | 关闭参考 Python 服务，只运行 Java 版本；模型未配置；SSE 不可用 | 内容工作台正常；Agent 无隐性 Python 依赖；未配置明确提示；断线可查询降级 |
| AC-31 | 从基线 SHA 重新检出并核对参考映射与复用清单 | 能定位真实文件/符号；保留、改编、新增有区别；M0 证据真实且不冒用其他版本 |
| AC-32 | 满队列、排队取消、运行取消但本地请求未退出、连续调度拒绝 | 不超过物理并发/容量上限；资源只回收一次；无悬挂槽和句柄泄漏 |
| AC-33 | 已产生候选稿后模型失败/取消/截断；尝试绕过建议接口采纳候选 | 无 PENDING 建议可采纳；候选仅作为诊断记录；正式正文不变 |

AC-01 至 AC-33 全部通过后才视为 MVP 完成。本文列的是待执行的验收要求，不是已通过的测试报告。

模型执行链路中的确定性要求使用模拟模型验证；真实模型的建议质量另行人工核查，不以“每次都会调用同样的工具”作为真实模型验收要求。至少提供两个工具路径不同的模拟场景，证明循环并非固定调用脚本。

对照上游时比较保留的行为约束，而非逐字比较生成内容或强求相同工具顺序。上游不具备同语义接口的新增规则，只验证本项目需求，不伪造上游对照结论。测试至少分为无外部模型单测、MySQL 事务/并发集成测试、前后端端到端测试和少量真实模型验证。

### 10.2 固定演示数据

准备一个作品、两个短章节和三条设定。示例人物“林舟”在设定中不会游泳，第一章因恐惧拒绝下水，第二章在没有交代训练或能力变化的情况下独自潜入深水区。

演示任务：“检查第二章与已有设定是否存在需要解释的矛盾，结合第一章给出修改建议。”系统应展示实际查阅内容与建议依据；文学上的例外或情节转折仍由用户判断。

真实模型至少记录五次固定输入的运行结果，覆盖无须修改、生成建议、缺少设定、较长正文和可能的情节矛盾。人工检查建议是否保留主要剧情、是否引用实际读取内容、是否出现无依据补充；保留发现的问题，不宣称绝对正确率。

### 10.3 校招演示顺序

先展示内容编辑和一次完整 Agent 任务，再展示建议尚未采纳时正文不变；随后采纳并查看新版本。最后演示一次并发版本冲突，以及一次取消或失败恢复查询，说明后端如何保证状态和数据一致。

项目说明需区分产品参考/前端复用与独立实现的 Java 代码。展示重点是可验证的能力和设计取舍，不以简单配置已有框架冒充独立实现通用 Agent 平台。

## 11. 开发阶段与发布门槛

| 阶段 | 前端与参考工作 | 后端与测试交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| M0 基线验证与映射 | 固定 SHA，启动独立参考环境；记录真实请求/事件；列出前端组件和初始化依赖 | 沿 REF-01 至 REF-12 阅读关键链路；完成行为对照和裁剪决策；确认模型工具调用协议 | 参考场景实际跑通；无法确认的行为有明确记录；基线/迁移清单可复核 |
| M1 内容基础 | 精简入口、作品/章节工作台、纯文本编辑、设定抽屉 | 内容 API、版本保存、历史、迁移脚本、基础环境版本锁定 | 不调用模型也可完成编辑闭环；并发保存与本地草稿保护可验证 |
| M2 只读 Agent 闭环 | 任务提交、查询、真实步骤记录、错误/停止状态 | 运行受理/句柄/有界执行器、三个只读工具、显式循环、消息与调用持久化、取消/超时/事件表 | 模拟模型和真实模型均能查阅并分析；刷新可查询；不依赖原 Python 服务 |
| M3 受控修改 | 差异对比、整体接受/拒绝、冲突交互 | 第四个建议工具、候选与发布分离、采纳事务、状态竞争和失败回滚 | 接受、拒绝、重复提交、并发冲突、失败候选均有自动测试 |
| M4 联调与发布验收 | SSE 接入、断线与缓存更新、空态/异常态 | 数据库游标跟读、重启/存储故障回归、资源泄漏检查、固定演示数据 | AC-01 至 AC-33 通过；基线证据、启动与排错文档齐全 |

M0 的环境验证和阅读不能被“看了 README”替代；M1 的基础页面可与 M0 并行，但进入 M2 前应完成运行链路验证与裁剪决策。关键并发、事务和持久化约束随对应功能实现；M4 是补齐联调和验证，不是最后才设计任务状态。

记录实际 SHA、环境、命令、模型配置（去密钥）、关键请求/事件、源码入口、结果和失败原因。格式可用脱敏 JSON 与文字记录，不要求制作视频。没有实际观察到的行为标记为“仅静态阅读/待验证”，不能预填为通过。
